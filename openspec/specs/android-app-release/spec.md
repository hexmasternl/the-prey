# android-app-release Specification

## Purpose
Defines how CI verifies, versions, signs and publishes the Kotlin Android app to the Play Console as a private (internal testing) release, how it writes the release notes in English and Dutch, and when it records the shipped version as a GitHub release.

## Requirements

### Requirement: Only the Kotlin app has a release pipeline
CI SHALL contain exactly one app release workflow, for the Kotlin app in `app/src`. No workflow, documentation page or required secret for the removed Ionic or .NET MAUI clients SHALL remain in the repository.

#### Scenario: Legacy workflows absent
- **WHEN** the repository's workflow directory is listed
- **THEN** it contains no Ionic or MAUI release workflow and exactly one workflow that builds the Android app

#### Scenario: No legacy references
- **WHEN** the workflows and docs are searched for the removed clients' project paths or workflow names
- **THEN** no match is found outside archived OpenSpec changes

### Requirement: App changes are verified before they ship
The app release workflow SHALL run the app's lint and unit tests for every pull request and every push to `main` that touches the app or the workflow, and SHALL NOT build or publish a release bundle when they fail.

#### Scenario: Pull request
- **WHEN** a pull request changes files under `app/src`
- **THEN** lint and unit tests run and no bundle is published and no release is created

#### Scenario: Failing tests on main
- **WHEN** a push to `main` changes the app and a unit test fails
- **THEN** the workflow fails without publishing to Google Play

#### Scenario: Unrelated change
- **WHEN** a push to `main` changes only backend or website files
- **THEN** the app release workflow does not run

### Requirement: App version comes from the shared version line
The workflow SHALL take the app's `versionName` from the shared GitVersion workflow as a plain `major.minor.patch` value and SHALL fail before building when that version is empty or carries a pre-release label.

#### Scenario: Version from main
- **WHEN** the shared version workflow yields `1.4.2` on `main`
- **THEN** the published bundle has `versionName` `1.4.2`

#### Scenario: Empty version
- **WHEN** the shared version workflow yields an empty version
- **THEN** the workflow fails before building and nothing is published

#### Scenario: Pre-release version
- **WHEN** the workflow is started manually on a branch whose version is `1.4.2-feature.3`
- **THEN** the workflow fails before building and nothing is published

### Requirement: Version code grows with the version
The workflow SHALL derive the bundle's `versionCode` deterministically from the version number, plus a configurable offset, so that a higher version always yields a higher code.

#### Scenario: Minor bump
- **WHEN** version `1.2.0` is built after version `1.1.9`
- **THEN** the `versionCode` of `1.2.0` is higher than that of `1.1.9`

#### Scenario: Patch beyond 99
- **WHEN** version `1.1.120` is built after version `1.1.99`
- **THEN** its `versionCode` is higher than that of `1.1.99` and lower than that of `1.2.0`

#### Scenario: Same version rebuilt
- **WHEN** a version that is already in Google Play is built again
- **THEN** the bundle gets the same `versionCode` and the Play upload is rejected

### Requirement: Private release on the internal testing track
On a push to `main` or a manual run, the workflow SHALL publish a signed release bundle for `nl.hexmaster.theprey` to the Play Console internal testing track as a completed release. It SHALL NOT publish to any other track.

#### Scenario: Successful publish
- **WHEN** a push to `main` changes the app and lint and tests pass
- **THEN** a signed bundle with the derived version is released on the internal testing track and only internal testers receive it

#### Scenario: Manual run
- **WHEN** the workflow is started manually on `main`
- **THEN** it publishes to the internal testing track without asking for a track

#### Scenario: Missing signing material
- **WHEN** a signing secret is missing or wrong
- **THEN** the workflow fails before uploading anything to Google Play

### Requirement: Bilingual release notes generated by Copilot
The workflow SHALL generate release notes with GitHub Copilot from the app commits since the last successful app publish, in English and in Dutch, each within Google Play's 500-character limit, and SHALL use them as the Play "What's new" text for both languages.

#### Scenario: Notes generated
- **WHEN** the workflow publishes a bundle and Copilot returns notes
- **THEN** the Play release shows the English notes for English users and the Dutch notes for Dutch users

#### Scenario: Notes describe app changes only
- **WHEN** commits since the last app publish touch both the app and the backend
- **THEN** only the commits that touch `app/src` are given to Copilot

#### Scenario: Notes too long
- **WHEN** Copilot returns a text longer than 500 characters for a language
- **THEN** the text sent to Play for that language is shortened to at most 500 characters

#### Scenario: Copilot unavailable
- **WHEN** Copilot fails, times out, or returns output that is not usable
- **THEN** the publish still happens with fallback notes in both English and Dutch, and the run shows a warning

### Requirement: GitHub release after the Play publish
After a successful Play upload, the workflow SHALL run the shared create-release step with the shipped version and the generated English and Dutch notes as the release body. It SHALL NOT create a release when the upload fails or for a pull request.

#### Scenario: New version
- **WHEN** the bundle for `1.4.2` is published and no release `v1.4.2` exists
- **THEN** the tag `v1.4.2` and a GitHub release whose body holds the English and the Dutch notes are created at the workflow's commit

#### Scenario: Release already exists
- **WHEN** a backend workflow has already created `v1.4.2` for the same version
- **THEN** the app workflow leaves that release unchanged and completes successfully

#### Scenario: Upload failed
- **WHEN** the Play upload fails
- **THEN** no tag or release is created by the app workflow
